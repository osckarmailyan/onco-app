# OncoExperts: инженерный аудит 22.11.2026

Редизайн и серверный сценарий записи подготовлены в существующем проекте. Приём реальной оплаты пока не готов к включению: боевые Supabase, ЮKassa, Resend, видеосвязь и вся цепочка подтверждения требуют проверки в целевом окружении. Онлайн-запись намеренно выключена; расписание по указанию владельца не формируется.

Актуальные условия: **10 000 ₽, 25–30 минут, интервал записи 30 минут, Оскар Маилян**. Единый источник — `lib/meeting-config.ts`; сумма и отображаемая длительность сохраняются в каждой записи.

## Финальная проверка новой записи

- Цена, длительность и сумма платежа задаются сервером. Клиент не может передать собственную цену или медицинские поля. Имя/email, UUID, версия согласия, Origin и размер тела проверяются; ошибки полей возвращают 400.
- Резервирование выполняется транзакцией с advisory lock, проверкой пересечений и уникальным активным бронированием интервала. Повторный UUID с теми же данными возвращает прежнюю запись; изменение данных с тем же UUID отклоняется.
- У ЮKassa используется стабильный ключ идемпотентности. Webhook сам по себе не подтверждает оплату: сервер читает платёж по авторизованному API и проверяет ID, metadata, сумму, RUB и test/live режим. Поздний статус не может откатить уже сохранённый терминальный статус.
- `duration_label` и сумма сохраняются при записи. Флаг поздней оплаты определяется по времени списания провайдера при первом сохранении успешного платежа и больше не пересчитывается по дате просмотра. Для такой записи нет обещания прошедшей встречи или видеоссылки в письме; в админке есть пометка «Нужно согласовать другое время».
- Подтверждение использует claim в БД и ключ идемпотентности Resend; ошибочная отправка не превращает оплату в неуспешную. Повторный webhook не создаёт обычного дубля письма. Строгая exactly-once доставка за пределами окна внешнего провайдера не заявляется.
- Публичные API не возвращают имя, email или видеоссылку. Статус одной записи защищён непредсказуемым bearer-токеном; лимиты запросов сохраняются в БД, IP хешируется HMAC. Секрет токенов должен оставаться стабильным.
- Исправлено вытеснение очереди сверки старыми orphan: service-only RPC исключает невосстановимые записи без ID до лимита 20, а успешно проверенные pending перемещаются в конец очереди. Это не освобождает неоднозначные интервалы и не удаляет данные.
- `BOOKING_ENABLED=false` закрывает создание новых записей и выдачу расписания. Статус и webhook уже созданных записей продолжают работать при сохранённых действительных ключах. Таблицы при таком откате сохраняются.

## Условия перед включением реальной записи

1. **База и старый доступ.** Применить обе проверенные миграции к выбранному тестовому, затем целевому Supabase. Миграция 002 закрывает клиентские права старой таблицы `cases`, добавляет запретительную RLS-политику, делает bucket приватным и сохраняет данные. В рабочей Supabase миграции не выполнялись; старый доступ нельзя считать закрытым лишь по изменению Next.js.
2. **Расписание.** Сейчас не создавать слоты. Когда владелец отдельно решит включить запись, добавить только согласованные реальные интервалы по 30 минут с рабочими приватными ссылками видеовстреч. Проверить часовой пояс и права участника.
3. **Платежи, чеки и почта.** Проверить магазин и режим ЮKassa, обязательные серверные настройки, webhook, схему чеков и настройки Resend. Ключи ЮKassa обнаружены основным потоком в локальном игнорируемом окружении; их значения здесь не читаются и не публикуются. Наличие ключей не подтверждает готовность магазина. При первой попытке 22.11.2026 кабинет не открывался из-за сетевого timeout. После входа в Safari было подтверждено сообщение ЮKassa об отключённой организации и расторгнутом прежнем договоре; повторное подключение отложено владельцем. Реальные платежи и письма не выполнялись.
4. **Проверка всей цепочки.** В тестовом окружении проверить оплату/отмену, повторный POST, потерю ответа, повторный webhook, сбой почты и письмо с рабочей видеоссылкой. SQL/unit tests не подтверждают доступность внешних сервисов. После этого отдельно решить вопрос включения `BOOKING_ENABLED=true`.
5. **Эксплуатация и тексты.** Проверить HTTPS, сильные ADMIN_USER/ADMIN_PASSWORD, правила доверенного proxy IP и фактические условия/реквизиты/согласия. Не возвращать публичные anon-политики медицинских данных при откате интерфейса. Инженерная проверка не является юридическим согласованием документов.

## Известные операционные ограничения

- Неоднозначные `pending` без сохранённого payment_id не освобождаются вслепую: после безопасного окна повтора или слишком близко к началу встречи требуется сверка оператором с ЮKassa. Иначе поздняя оплата могла бы привести к двойному бронированию.
- После потери ответа на POST повтор в той же открытой форме использует прежний UUID. Полное закрытие/перезагрузка формы не восстанавливает выбранный собственный pending-интервал автоматически: публичное расписание уже исключает его, а браузер хранит только fingerprint/UUID. Если переход к оплате не восстановился, нужен контакт с поддержкой; автоматического resume-сценария в этой версии нет.
- Для длительной эксплуатации нужна операторская сверка зависших платежей и доставки. Фоновый reconciliation job не добавлялся; механизмы текущей версии — webhook, страница статуса и ограниченная сверка при чтении расписания. Повторы email после crash ждут пятиминутного claim.

## Процесс публикации: диагностика 22.11.2026

Владелец разрешил выложить новую версию на существующий `oncoexperts.ru`, сохранив выключенными ЮKassa и расписание. Публикация выполняется из существующего каталога `onco-app` в прежний проект Vercel; новый хостинг и новая база не создаются.

- Соединение к `api.vercel.com` останавливается на этапе TLS и завершается таймаутом. Проверка сертификатов не отключалась.
- Официальный маршрут `https://vercel.com/api` отвечает на проверочные API-запросы. Это подтверждает доступность альтернативного маршрута, но само по себе не подтверждает успешную загрузку файлов, сборку или публикацию.
- Ранее сохранённая авторизация OAuth истекла; попытка обновления вернула `invalid_grant`. Вход восстановлен после подтверждения MFA владельцем. Токены, коды входа и другие учётные данные в документацию не записываются.
- Для CLI исследуется временное перенаправление запросов через официальный HTTPS-маршрут с обычной проверкой TLS. Особенности скрытого `--api` проверены в установленном CLI: основной клиент и загрузчик по-разному соединяют base URL и путь. Решение не считается проверенным до завершения реального deployment.
- `BOOKING_ENABLED=false` требуется и во время сборки, и в runtime. Страница `/request` предварительно формируется при сборке и фиксирует это значение; после выкладки нужно проверить, что она предлагает согласование по email, а платёжные действия и расписание закрыты.
- Редизайн опубликован 22.11.2026: `dpl_6xbeMTvfPGkSv2XyoVemxgy6UhjG`, исходный коммит `312cb5e7d20f000afeb8f5c9cc390a5f95909985`. Vercel вернул READY и aliasAssigned=true для `www.oncoexperts.ru` и `oncoexperts.ru`. Миграции рабочей Supabase и подключение ЮKassa в эту публикацию не входят.
